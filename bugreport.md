# Рассинхрон ранов cide

Баг-репорт для разработчика cide. Найдено за два дня работы оркестратора с тремя ролями через MCP-инструменты cide. Главная проблема: cide приписывает ран не той задаче и держит очередь задачами, у которых живого рана уже нет. Идентификаторы задач и ранов взяты из трекера проекта. Код и данные продукта сюда не попали.

| | |
|---|---|
| Когда | 2026-10-20 — 2026-10-21 |
| Как вызывалось | MCP: `cide_task_create`, `cide_task_update`, `cide_agent_dispatch`, `cide_agent_runs`, `cide_agent_stop`, `cide_agent_integrate` |
| Роли | architect, backend-dev, frontend-dev. У каждой своя git-worktree на ветке `cide/<role>-<task>`, харнесс Claude Code |
| Лимиты | Не больше 2 ранов одновременно на проект |

## 1. Dispatch на задачу B отказывает и называет ран, который работает над задачей A

**Важность:** высокая

**Шаги**
1. Подряд создать две задачи с исполнителями через `cide_task_create`: t-51 для `backend-dev` и t-52 для `frontend-dev`. `touches` у них не пересекаются.
2. Вызвать `cide_agent_runs`.
3. Вызвать `cide_agent_dispatch(agent: frontend-dev, task: t-52)`.

**Что произошло**

Запустился только один ран: `5452a379`. В `cide_agent_runs` он один, `backend-dev` на t-51. Рана на t-52 нет ни в активных, ни в завершённых (проверено с `includeFinished` и `agent: frontend-dev`). Dispatch при этом отказывает:

```
cide_agent_dispatch: `frontend-dev` is already on t-52: run 5452a379-… [running]. A role gets one run per task…
```

Frontend-dev на t-52 так и не стартовал. Только после того как t-51 интегрировали и пометили done, тот же dispatch прошёл и создал новый ран `2ad3f380`.

**Ожидалось**
- Задачи с непересекающимися `touches` запускаются параллельно, лимит 2 это позволяет. Если нет, t-52 стоит в очереди с понятной причиной.
- Отказ называет ран, который действительно относится к этой роли и задаче.

**Гипотеза:** вероятно, при создании двух задач подряд привязка «роль + задача → ран» записывается не туда: ран второй задачи затирает ран первой или получает её id.

## 2. Задача в review без живого рана часами держит очередь

**Важность:** высокая

**Шаги**
1. Роль заканчивает работу над задачей без `touches` (t-47) и переводит её в review. Ран остаётся idle, «parked at its prompt».
2. Остановить ран через `cide_agent_stop`, после этого он exit 129.
3. Поставить в работу другие задачи без `touches` (t-36, t-24).

**Что произошло**

И до остановки, и после неё новые раны висят в очереди:

```
waiting: t-47 holds this task declares no `touches`, so it runs alone
```

Очередь освободилась, только когда t-47 вручную перевели в inbox. Позже то же повторилось с t-36 в review: ран backend-dev на t-47 простоял в очереди около 5 часов («started 5h ago | worked a moment»). Idle-ран, который закончил ход, тоже держит слот, пока его не остановишь вручную.

**Ожидалось**
- Блокировку «runs alone» держит живой ран, а не статус задачи. Задача в review, у которой рана нет, не мешает другим.
- Если такое поведение задумано, сообщение очереди говорит, как освободить очередь: перевести задачу в другой статус, указать `touches` или интегрировать.

## 3. Перевод в todo запускает прежнего исполнителя, и сменить его уже нельзя

**Важность:** средняя

**Шаги**
1. Задача в inbox, исполнитель `architect` (он писал спецификацию).
2. Чтобы передать реализацию другой роли, сначала вызвать `cide_task_update(status: todo, body, touches)`.
3. Затем вызвать `cide_task_update(assignee: backend-dev)`.

**Что произошло**

Шаг 2 сразу поставил в очередь ран `architect`. Шаг 3 отказал целиком:

```
t-47 was not changed… A run is working on it right now (Architect) from the body it was started on…
```

При этом ран был в статусе queued и ещё не начинал работу. Пришлось отменять его через `cide_agent_stop` и повторять смену исполнителя. После этого пришло уведомление «Architect failed on task t-47».

**Ожидалось**
- Смена исполнителя у задачи, ран которой только в очереди, отменяет этот ран сама. Или текст ошибки говорит, что ран queued и его можно отменить.
- Хорошо бы `cide_task_update` менял статус и исполнителя за один вызов, тогда этой гонки не будет.

## 4. `touches` в соседнем репозитории не изолируются worktree

**Важность:** средняя

**Шаги**
1. Проект cide открыт в одном репозитории, а задача правит соседний: `touches: ["../repo-b/src/…"]`.
2. Назначить задачу роли, которая работает в своей worktree основного репозитория.

**Что произошло**

Роль создала ветку `cide/frontend-dev-t-52` прямо в основной рабочей копии соседнего репозитория и переключила её. На этой рабочей копии работал локальный дев-сервер пользователя: он стал отдавать агентскую ветку вместо master. Это выяснилось только при ревью.

**Ожидалось**
- Для путей за пределами корня проекта cide либо создаёт отдельную worktree соседнего репозитория, либо явно предупреждает при создании задачи, что изоляции нет.
- Пересечение `touches` с путями вне проекта проверяется так же, как внутри.

## 5. Уведомления о ранах вводят в заблуждение

**Важность:** низкая

**Что произошло**
- Ран, отменённый через `cide_agent_stop` до старта, приходит как «Architect **failed** on task t-47», хотя ответ stop был «Cancelled… before it started; nothing ran».
- Пришло «handed its turn back on t-36», а `cide_agent_runs` в тот же момент показывал этот ран как running: он уже обрабатывал новые инструкции.
- Уведомления «2 subagent turns just ended» склеивают в одно сообщение остановки, которые запросил сам оркестратор, и настоящие завершения ходов. Из-за этого оркестратор лишний раз перечитывает задачи.
- В уведомлении стоит текущий заголовок задачи. После переименования отчёт старого рана выглядит как отчёт по новой работе.

**Ожидалось:** отдельный статус `cancelled`, уведомления в порядке событий, а остановки по запросу оркестратора помечены как его собственные действия.

## 6. Промпт запуска противоречит телу задачи

**Важность:** низкая

**Что произошло**

В теле задачи было «не коммитить, не собирать». Роль всё равно закоммитила и собрала проект и объяснила это так:

```
Правило «не коммитить/не собирать» из тела задачи нарушил: промпт запуска прямо требовал коммиты и чекбоксы.
```

В другом ране той же роли auto mode харнесса отклонил миграции и `psql`. Роль остановилась, и проверки пришлось делать основной сессии.

**Ожидалось:** задокументированный приоритет инструкций (тело задачи против промпта запуска). Ещё лучше настройка на уровне задачи или роли, например «без коммитов», которую учитывает и промпт запуска.

## 7. Задача стала done без явного действия оркестратора

**Важность:** уточнить

**Что произошло**

Задача t-36 была в review. На её ветку вызвали `cide_agent_integrate`, а позже добавили комментарий. Ответ на комментарий показал `t-36 [done]`, хотя статус done оркестратор не ставил. В задаче оставалась работа (группы 3–4), её пришлось вынести в новую задачу.

**Вопрос:** integrate сам переводит задачу в done? Если да, пусть ответ integrate об этом говорит, и нужен способ влить промежуточный результат, не закрывая задачу.

---

Задачи и раны указаны по идентификаторам трекера `.cide/tasks.json`. Тексты ошибок и сообщений процитированы дословно из ответов MCP-инструментов cide.
